A machine-learning model that takes a source, a destination, and the current time — and returns how long the trip will actually take, trained on real GPS traces of Dhaka traffic.

01The Problem

One query, one number: minutes to get there

Input → Output

src = (lat, lon)
dst = (lat, lon)
time = now
──────────────
duration = f(src, dst, time)

Why it matters

  • Dhaka traffic varies wildly by hour, day, and route — a fixed "average speed" estimate is unusable.
  • Ride-hailing ETAs, delivery windows, and shuttle scheduling all need a trustworthy travel-time number, not just a map distance.
  • Deployed and tested on a real 135-leg shuttle route sheet for a live use case (see Slide 13).

Each trace is a GPX/XML file: an ordered list of (lat, lon, timestamp) points recorded by a real device travelling through the city. Started with 2 files — clearly not enough — so the full public Dhaka trace archive was downloaded systematically, tiling the city into sub-0.25° boxes to respect the API's per-request area limit, then paging through every box.

04Features · Spatial & Routing

What the model actually sees — part 1

FeatureHow it's computed
haversine_distance_kmGreat-circle straight-line distance between src and dst.
bearing_degreesCompass direction from src to dst (0–360°).
osrm_route_distance_kmReal road-network distance from a self-hosted OSRM engine (Docker, MLD algorithm, built from the Bangladesh OSM extract).
osrm_free_flow_duration_secOSRM's own no-traffic travel-time estimate for that road route.
route_directness_ratiohaversine ÷ osrm_route_distance — how winding the real road path is vs. a straight line.
src_zone_id / dst_zone_id / od_zone_pair_idWhich cell of the fixed 20-cell city grid src/dst fall in (Slide 8).

Raw lat/lon are used to compute all of these — never fed to the model directly (Slide 7).

04Features · Temporal & Historical

What the model actually sees — part 2

FeatureHow it's computed
hour_sin / hour_cosCyclical encoding of time-of-day (so 23:59 and 00:01 sit next to each other, not far apart).
traffic_period_bucketDiscrete bucket — night / morning_offpeak / morning_rush / midday / evening_rush / evening_winddown — instead of raw hour. Adopted from a teammate's suggestion; validated to help the tree models split on real traffic regimes rather than noisy exact minutes.
day_of_week, is_friday, is_saturday, is_weekendBangladesh weekend is Friday+Saturday, not Sat/Sun — encoded explicitly.
is_holidayFixed-date national holidays only (lunar Islamic holidays shift yearly — known limitation, Slide 12).
rush_hour_flag1 if 8–10am or 5–9pm.
historical_avg_speed_kmhLooked up from training data: mean real speed for this OD-zone-pair at this time bucket → falls back to zone-pair only → time-bucket only → global mean, whichever has enough support. Recomputed per CV fold to avoid leakage.

Target: duration_seconds, trained in log-space (log_duration) and exponentiated back for reporting.

05Design Choice

Why not just feed the model raw lat/lon?

The trap

A tree model given raw coordinates learns to split on exact latitude/longitude thresholds it saw in training. A brand-new src/dst pair a few hundred meters from anything seen before gets no meaningful split — the model has no notion of "nearby."

What we do instead

  • Lat/lon are used only as inputs to formulas — distance, bearing, and which fixed zone a point falls in.
  • The model is trained on the zone id / od_zone_pair_id categories, plus continuous distance and route features — quantities that generalize to any new coordinate, because every coordinate maps into one of the 20 zones.
  • This is exactly what makes inference on a never-seen-before src/dst pair possible (Slide 13).
06Zoning

Why a fixed 4×5 grid, not data-driven clusters?

The problem with K-Means zones

K-Means clusters only where GPS traces already exist. Areas the traces never visited simply have no zone — so a query touching one of those areas at inference time falls completely outside anything the model learned.

The fix: a fixed geographic grid

Split Dhaka's full bounding box into a uniform 4×5 grid (20 cells) regardless of data density. Every possible coordinate in the city — visited or not — lands in a real, defined zone.

07Validation Strategy

Grouped 5-fold cross-validation, by trip

Why grouped — not plain random K-fold

One trip produces several rows (0.3/1/3/8 km sub-samples, all sharing the same route and traffic conditions). A random split can put some of a trip's rows in train and others in validation — the model "recognizes" that trip and validation looks artificially good.

GroupKFold(groups=trip_id) keeps every row from one trip on the same side of the split, every fold.

Why 5 folds

Standard bias/variance trade-off: enough folds that each validation slice is large enough to trust (≈1,750 rows / ≈61 trips per fold here), without the training cost of something like 10-fold on a modest 304-trip dataset.

08Hyperparameter Sensitivity

What happens if you change these knobs?

KnobTurn it downTurn it up
Grid size
currently 4×5 = 20 cells		 Fewer, bigger zones → more data per zone (robust averages) but coarser location signal → higher error inside each zone. More, smaller zones (e.g. 10×10) → sharper spatial signal, but zones get sparse fast → historical lookups fall back to coarser tiers more often, and more zones go completely unvisited.
CV folds (k)
currently 5		 k=3 → faster, but each validation slice is bigger relative to train, and the performance estimate gets noisier. k=10 → more stable estimate, but 2× the model fits for a 304-trip dataset — diminishing returns here.
min_support
min trips before trusting a historical average		 Lower → uses averages backed by only 1–2 trips → noisy, overfits to a handful of samples. Higher → more queries fall back to coarser period-only / global averages, losing the localized signal that helps most.

All three were tuned empirically against out-of-fold MAE, not picked arbitrarily — the values shown throughout this deck are what won.

Metrics — why these three

  • MAE — average error in seconds, easy to communicate ("off by ~8 minutes").
  • RMSE — penalizes big misses harder; exposes whether a model is occasionally wildly wrong.
  • MAPE — relative error, comparable across short and long trips.

Why Ridge fails, why LightGBM is missing

Ridge destabilizes: one-hot encoding 85 OD zone-pair levels for a modest number of trips is a high-dimensional sparse setup that blows up once exponentiated out of log-space.

LightGBM crashed with a native access-violation on this Windows/Python 3.12 environment — an environment DLL conflict, not a data or modeling issue. Dropped from the comparison, documented as a known limitation.

10Problems Faced

What actually went wrong along the way

Data & signal

  • Started with only 2 GPX files — solved by systematically downloading the full public Dhaka trace archive (89 traces, 270 API pages).
  • GPS glitches and OSRM road-snap errors produced impossible speeds — filtered with explicit QC thresholds.
  • K-Means zones left real gaps in city coverage — replaced with a fixed grid (Slide 8).
  • No offline calendar for lunar Islamic holidays (Eid, Ashura, …) — only fixed-date holidays are flagged; known limitation.

Modeling & environment

  • A naive random split leaked correlated sub-trajectories between train/val — fixed with grouped CV by trip_id.
  • Historical features frozen from one static split leaked fold information — fixed by recomputing them per fold.
  • LightGBM crashed natively on this machine — dropped, documented as environment-specific.
  • 8 GB RAM host + Docker OSRM containers caused intermittent out-of-memory failures — mitigated by stopping unused containers during training.
11Inference & Deployment

Predicting a brand-new src/dst pair

The inference pipeline

  • Raw (src, dst, time) query comes in — no history needed for this exact pair.
  • Compute haversine, bearing, live OSRM route; assign both points to a grid zone (always succeeds — the grid covers the whole city).
  • Look up historical speed via the 3-tier fallback; encode time-of-day and calendar features.
  • Feed the row to the bundled XGBoost and Random Forest models — both packaged with the zone grid, lookup tables, and feature schema in one inference_bundle.joblib file for portability.

Real-world validation

Tested against a genuine 135-leg shuttle route sheet (multi-stop pickup routes), predicting each leg's travel time chained leg-by-leg from its actual departure time.

12Summary

Where this lands, and what's next

Result

Random Forest, trained on the fixed-grid feature set with per-fold historical speed lookups, is the deployed model — MAE 495s (~8.3 min), beating XGBoost, both calibrated and naive baselines, and Ridge regression, under leakage-safe grouped cross-validation.

Known limitations & future work

  • Single city (Dhaka only), ~300 trips — sparse zone-pairs still fall back to coarser averages.
  • No lunar holiday calendar; historical speed is static, not live traffic.
  • Next: more traces per sparse zone-pair, a live traffic feed, road-type/weather features.
